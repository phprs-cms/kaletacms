# 4.0 data model – design

Status: draft for the owner's decision (3.7, October 2026). There is no code in this document. It covers six data-model
questions, gives the evidence from the code and the schema for each, and ends with a phased plan and the open questions.

Sources: `system/sql/schema.sql` (92 tables, 725 columns), `CLAUDE.md`, the CPO inventory (INV-6, INV-7, INV-15 and INV-17)
and the migration inventory of the owner's first five sites (8 October 2026). The line numbers refer to the 3.7 branch.

## 0. Ground rules that every option below must respect

- **Nothing breaks.** Existing sites, links, e-mails already sent, cron jobs, exports and MCP/OAuth connections keep
  working. MCP tool names, parameters and their Czech aliases stay (`Mcp\Translator`, `tools/contracts/mcp-tools.json`).
- **Supported databases:** MySQL 8 and MariaDB 10.6+ (`README.md:53`). CI runs the migration test on MySQL 8.4,
  MariaDB 10.6 and MariaDB 11.4 (`.github/workflows/kontrola.yml:56-57`). Whatever we choose must work on MariaDB 10.6.
- **Shared hosting.** We have no root access, no `pt-online-schema-change` or `gh-ost`, and no maintenance window. Migrations
  run on the first request after an update (`Front\Kernel::__construct`, `Migration::safe`), and a failing one is logged
  while the site keeps running. That is why every schema change must be additive or atomic.
- **The migration chain.** `tools/test-migrations.sh` builds a database from v1.0.0, runs every migration, and compares the
  result with a clean install. A data migration (`NNNN-*.php`) must have the highest number of its release, because older
  updater code only knows `.sql` (`CLAUDE.md`, "2.0 bez vrstev kompatibility").

**The pattern used throughout: expand, migrate, contract.**
1. A 3.x release *expands* the schema: it adds columns, keys or wider types next to the old ones. Code from that release
   reads both forms.
2. Data moves in batches through the background jobs (`Core\Scheduler`), never in one long request.
3. Only a later major release *contracts*: it removes the old form.

**Rollback** always means installing the previous release's code. Our migrations never run backwards, so every expanded
schema must stay readable by the code of release N-1. The one exception is noted in each section below.

## 1. Collation: `utf8mb4_czech_ci` on every table

### Evidence

- All 92 tables are `DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_czech_ci` (`schema.sql`, every `CREATE TABLE`). The test
  database is created the same way (`tools/test.sh:21`).
- Code relies on the collation being case-insensitive. For example, `Front\Kernel::redirectRule` falls back to "the
  database compares without regard to case" (`Kernel.php:996`). Redirect sources have a unique key
  (`uq_presmerovani (z_adresy)`, `schema.sql:308`).
- Search does not depend on the collation. `Core\Search::normalize` strips diacritics and keeps only `a-z0-9`
  (`Search.php:15-19`), and `MATCH … AGAINST` runs on that normalized column.
- 46 queries sort by a name or title (`ORDER BY … nazev|titulek|name|…`) in `system/src`.
- There are 23 unique keys. Those on human text are `uq_user`, `uq_role_nazev`, `uq_odberatel_email`, `uq_presmerovani`
  and `ux_popupy_adresa`. Slugs (`seo_link`) are ASCII `[a-z0-9-]`, so the collation does not affect their uniqueness.

**Measured on the local MySQL (26.7) with `SELECT … COLLATE …`:**

| Comparison | `czech_ci` | `cs_0900_ai_ci` | `0900_ai_ci` | `unicode_ci` |
|---|---|---|---|---|
| `'kos' = 'koš'` | 0 | 0 | **1** | **1** |
| `'a' = 'á'` | 1 | 1 | 1 | 1 |
| `'a ' = 'a'` (trailing space) | 1 (PAD SPACE) | – | **0** (NO PAD) | 1 |
| `'🍕' = '🍔'` | **1** | – | 0 | **1** |
| `'chata' LIKE 'c%'` | 1 | 1 | 1 | – |

**Sort order of the same 13 words:**

- `czech_ci` and `cs_0900_ai_ci`: cesta čaj ďábel dub hrad **chata** izba rak řeka sova šum zebra žába
- `0900_ai_ci` and `unicode_ci`: **čaj cesta chata** ďábel dub hrad izba rak řeka sova šum **žába zebra**

### What this means

- **Czech sites need the current collation.** Under it č, ř, š, ž and ch are letters of their own, so "chata" sorts after
  "hrad". A move to `0900_ai_ci` or `unicode_ci` puts "čaj" before "cesta". It also makes `kos` equal to `koš` in every
  unique key and in every `WHERE x = ?`.
- **Non-Czech sites pay for the Czech rules.** English, German and Arabic lists put "Chicago" after "Hotel". This is a
  sorting problem only. Equality is affected only through č/ř/š/ž, which those languages barely use.
- **There are two silent equality bugs under UCA 4.0** (`czech_ci`, `unicode_ci`):
  - Different emoji compare equal.
  - Trailing spaces are ignored.
  Neither matters for slugs, but both matter for names in unique keys (`uq_role_nazev`) and for name lookups during
  imports.
- **MySQL and MariaDB differ:**
  - `utf8mb4_czech_ci` is the only Czech collation that both MySQL 8 and MariaDB 10.6 have. That is probably why it was
    chosen.
  - MySQL 8 adds `utf8mb4_cs_0900_ai_ci` and `_as_cs`.
  - MariaDB 10.10+ adds the UCA 14.0 family (`utf8mb4_uca1400_ai_ci`, `utf8mb4_czech_1400_ai_ci`). MariaDB 10.6 has
    neither family.
  - Recent MariaDB releases accept the `0900` names as aliases. Verify that in CI before relying on it.
  - The defaults differ too. MySQL 8 uses `0900_ai_ci`. MariaDB 10.6 uses `general_ci`, and newer MariaDB releases use
    UCA 14.0.
  - So a database created by a hosting panel without an explicit collation behaves differently per server. We always
    give the collation explicitly, and that must stay.
- **Converting is expensive and can fail.** `ALTER TABLE … CONVERT TO` rebuilds every table and every index (a full copy).
  The conversion fails on unique keys that become duplicates under the new rules. Examples: two redirect sources `/kocka`
  and `/kočka` from a WordPress import, or `Role A` and `Role A ` with a trailing space.

### Options

| | Option | Pros | Cons |
|---|---|---|---|
| A | Keep `utf8mb4_czech_ci` everywhere (status quo) | Zero risk; one test matrix; Czech sorting correct | "ch" rule and emoji equality for every site |
| B | Move everything to `utf8mb4_unicode_520_ci` (exists on both) | Language-neutral; fixes emoji for most characters | Breaks Czech sorting; full table rebuild; duplicate-key failures |
| C | `utf8mb4_0900_ai_ci` / `uca1400_ai_ci` | Modern UCA | Not on MariaDB 10.6; differs per server; same rebuild risks as B |
| D | Choose the storage collation per site at install | Right sort per site | Two schemas to test; "Illegal mix of collations" when old and new tables meet; migrations must inherit the site's collation |
| **E** | **Keep the storage collation (A) and fix the semantics where they matter (recommended)** | No mass conversion; each change is small and testable | Some explicit `COLLATE` in queries |

### Recommendation (E)

1. **Storage stays `utf8mb4_czech_ci`.** New tables, including those of 4.0, keep it, so joins never mix collations.
2. **Sort by the site language, not by the storage collation.** Visitor-facing and admin lists that sort by name or title
   use one helper that returns `ORDER BY x COLLATE <c>`. It maps:
   - `cs` to `utf8mb4_czech_ci` and `sk` to `utf8mb4_slovak_ci`
   - `de` to `utf8mb4_german2_ci` and `pl` to `utf8mb4_polish_ci`
   - any other language to `utf8mb4_unicode_520_ci`

   All of these collations exist on both servers. An explicit `COLLATE` in `ORDER BY` costs an index-less sort. That is
   fine for our list sizes, which are hundreds of rows, and the 46 call sites are easy to find.
3. **Change the collation of single columns where it is wrong:**
   - **Tokens and hashes:** `token`, `token_hash`, `otisk`, `client_id`, `public_key` move to `ascii_bin`. That is exact,
     smaller and faster. All of them are hex or base64, so no duplicates can appear. The change is safe in 3.x.
   - **Redirect sources:** `z_adresy` is stored normalized (lower-case, percent-decoded) and compared in PHP. The column
     then moves to `utf8mb4_bin`. This must be one step together with `Kernel.php:996`, and it needs a data migration
     that resolves the collisions it finds (`/kocka` vs `/kočka`) and reports them. It is a 4.0 change.
   - **Names in unique keys** (`uq_role_nazev`) are validated in PHP: trim them, and compare emoji there.
4. **Revisit in 5.0.** By then MariaDB 10.6 is out of support, and UCA 14.0 with a Czech tailoring exists on both servers.

**Migration and rollback.** Step 2 is code only. Step 3 changes columns one at a time with `ALTER TABLE … MODIFY …
COLLATE`, a small table copy on SMB-sized tables. The old code keeps working with the binary collation on tokens, because
it compares exact strings anyway. The redirect change needs both sides. Its rollback is a reverse `MODIFY` in a
hand-off script, because the lower-cased data stay valid for the old code.

**Risks:** an explicit `COLLATE` that differs from the column's collation inside a join. The helper is used only in
`ORDER BY`, never in `WHERE`.

**Effort:** S for step 2, S for tokens, M for redirects.

## 2. `CHAR(2)` language codes to BCP 47 (`pt-BR`, `zh-Hant`)

### Evidence

- **Twelve language columns are two characters wide:**
  - `CHAR(2)` columns:
    - `ka_uzivatele.jazyk` (`schema.sql:34`), `ka_kategorie.jazyk` (`:83`), `ka_novinky.jazyk` (`:116`) and
      `ka_stranky.jazyk` (`:245`)
    - `ka_casti.jazyk`, which is part of the primary key (`:262`)
    - `ka_kolekce_polozky.jazyk` (`:594`), `ka_kolekce_sablony.jazyk`, part of the primary key (`:609`), and
      `ka_menu.jazyk`, part of the primary key (`:642`)
    - `ka_newsletters.language` (`:790`)
  - `VARCHAR(2)` columns: `ka_facts.language`, part of a unique key (`:956`), `ka_fact_history.language` (`:970`) and
    `ka_bookings.language` (`:1365`)
- **Code assumes two letters in 22 places (`[a-z]{2}`):**
  - The router reads the language prefix with `#^/([a-z]{2})(/.*)?$#` (`Front/Kernel.php:80`), and
    `App::url()` uses `#^([a-z]{2})(?:/|$)#` (`App.php:114`).
  - Per-language setting keys use `site_name_<xx>` and `popis_webu_<xx>`:
    - in admin settings (`Admin/Modules/Settings.php:748`) and old settings keys (`OldSettingsKeys.php:126`)
    - in the Translator (`Translator.php:700`), export (`SiteExport.php:217`) and import (`SiteImport.php:848`)
  - The other places:
    - link handling: `LinkHealing.php:109` and `Links.php:234`
    - import validation: `SiteImport.php:598` and `Blueprint.php:77`
    - MCP input: `FactTools.php:21` and `FactTools.php:43`
  - The importers lose information. Joomla's `pt-BR` becomes `pt` (`Import/Joomla.php:223`), and a Drupal `pt-br` is
    dropped (`Import/Drupal.php:221`).
- **`Language::AVAILABLE`** (`Language.php:24`) and **`Language::CODES`** (`Language.php:68`) list 41 codes, all two
  letters. The fallback is `cs` (`Language.php:106`). Each entry already carries its ICU locale (`cs_CZ`), so the
  formatting side is ready for regions.
- `''` means "the default language" in every table. That stays.

### What changes and what does not

- **Every two-letter code is already a valid BCP 47 tag.** No stored value has to be rewritten. The change is only:
  - wider columns
  - wider patterns
  - a canonical-case function
- **Canonical form.**
  - Store lower-case tags: `pt-br`, `zh-hant`, `sr-latn`. Then `=` comparisons and URL prefixes need no case handling.
  - `<html lang>`, `hreflang`, Intl and the feeds get the canonical case (`pt-BR`, `zh-Hant`) from one function,
    `Language::tag()`.
- **URLs.** The prefix is the lower-case tag: `/pt-br/`, `/zh-hant/`. The router keeps accepting only enabled versions
  (`Language::additional`), so a page slug that looks like a tag is captured only when that language is switched on.
- **Settings keys** become `site_name_pt-br`. All five patterns move to one helper.
- **Dictionaries** become `system/jazyky/pt-br.php`, with the fallback chain `pt-br`, then `pt`, then `en`.
- **`zh` is ambiguous** (Hans or Hant). Decide whether the existing `zh` means `zh-Hans`, which is the most likely, or
  stays a plain macro-language tag.

### Options

| | Option | Notes |
|---|---|---|
| A | Keep two letters | Blocks `pt-BR`/`pt-PT`, `zh-Hans`/`zh-Hant`, `sr-Latn`/`sr-Cyrl`, `en-GB`/`en-US` |
| B | Language and region in separate columns | Doubles every key; nobody else does it |
| **C** | **BCP 47 tag in `VARCHAR(35) CHARACTER SET ascii` (recommended)** | RFC 5646 recommends supporting 35 characters; ASCII keeps keys small |

### Migration (zero downtime, full rollback)

1. **3.x, expand.**
   - Widen the twelve columns to `VARCHAR(35)` with the ASCII character set. On MySQL 8 and MariaDB, the change from
     `CHAR(2)` to `VARCHAR` copies the table, but the tables are small (pages, news, menu). On `VARCHAR(2)` the widening
     is in-place.
   - Primary keys that contain `jazyk` (`ka_casti`, `ka_menu`, `ka_kolekce_sablony`) are rebuilt by the same `ALTER`.
   - Code accepts the long tags everywhere (the 22 patterns), but `Language::AVAILABLE` still offers only two-letter codes.
   - **Rollback:** the 3.(x-1) code reads `VARCHAR(35)` columns that hold two-letter values without noticing.
2. **3.x+1 or 4.0.**
   - Add the regional entries to `AVAILABLE`: `pt-br`, `zh-hant` and others, by demand.
   - The importers keep the full tag (`pt-BR` from Joomla, Polylang and WPML).
   - **Rollback:** the old code meets rows with `pt-br`. It ignores them, because `Language::siteColumn()` filters by enabled
     codes. Content in such a version is hidden but not lost.

**Risks:**
- An `ALTER` on a large `ka_novinky` (10k+ rows) takes seconds and locks writes. Run it in the background job, not on the
  first request.
- Hyphens in setting keys pass `Settings::verifyValue`, which only checks the value.

**Effort:** M.

## 3. Page slugs unique across all languages, to unique per language

### Evidence

- `ka_stranky` has `UNIQUE KEY uq_stranky_seo (seo_link)` (`schema.sql:252`). INV-6 calls this out: `/de/kontakt`
  cannot exist next to `/kontakt`.
- **The same applies to news and taxonomy:**
  - news: `uq_clanky_seo` (`:122`)
  - categories: `uq_topic_seo` (`:86`)
  - tags: `uq_stitky_seo` (`:202`). Tags have no language column at all.
- **Collection items already do it right:** `UNIQUE KEY ux_kolekce_polozky_seo (idk, jazyk, seo_link)` (`:600`). So
  pages and items behave differently today.
- **The router is already per language.** The page lookup is
  `WHERE seo_link = ? AND jazyk = ? AND smazano IS NULL` (`Kernel.php:372`).
- **The checks and the redirects are global:**
  - The admin check is global: "A page with this URL already exists." (`Admin/Modules/Pages.php:274-276`).
  - So is the MCP check (`Mcp/Tools.php:666-668`).
  - Imports pick free slugs globally (`WpImport.php:472,601`, `WebImport.php:260`, `Import/Batch.php:361`).
  - **Redirects ignore the language.** The language prefix is stripped before `requestedPath` is taken
    (`Kernel.php:80-88`), and `notFound()` looks up `presmerovani` with the path without the prefix
    (`Kernel.php:1051-1052`). So a redirect `stary` also fires for `/en/stary`.
- **Owner's sites:**
  - fysiomed.eu has 396 products × 2 languages, and its Arabic slugs carry an `-ar` suffix only because WordPress needs
    unique slugs too (inventory, fysiomed §6).
  - ictnwt.cz has 95 pages in Czech and English, with translated slugs.

### What routing and links need

1. **Lookups by language.** Every lookup by slug filters by language:
   - `Audit::resolves` and `Links`
   - `LinkHealing` (the pattern already allows a prefix, `LinkHealing.php:109`)
   - the MCP tools that take a slug (`get_page`, `preview_link` and others gain an optional `language`). This is
     additive, so the contract stays.
2. **Uniqueness checks per language.** `(jazyk, seo_link)` everywhere, and nested slugs (`parent/child`) inside one
   language.
3. **Redirects carry the language.**
   - Store the full public path including the prefix (`en/stary`). Keep looking up the unprefixed form for rows written
     before the change; those are default-language rows by definition, since no other version could have the slug then.
   - `Redirects::add` on a slug change writes the prefixed form for non-default versions.
4. **hreflang and the language switcher** already go through `preklad_z` and the translation's own slug. No change.
5. **Menus** link by page id. No change. Links typed into content (`/kontakt`) stay literal paths, as they are today.
6. **Sitemap and llms.txt** already iterate per version.

### Options

| | Option | Notes |
|---|---|---|
| A | Keep it global | Translations need artificial suffixes; WordPress multilingual imports collide (INV-23) |
| **B** | **`(jazyk, seo_link)` for pages, news and categories; collections stay global, items already per language; tags gain `jazyk` later (recommended)** | Matches collection items |

### Migration (zero downtime, full rollback)

1. **3.x, expand.**
   - Add `UNIQUE KEY (jazyk, seo_link)` next to the global key on `ka_stranky`, `ka_novinky` and `ka_kategorie`. This is
     an in-place index build. The global key implies the new one, so no row can fail.
   - Make every lookup and check language-aware, behind a setting `slugs_per_language` (off).
   - Write redirects with the prefix.
   - **Rollback:** the old code ignores the extra key.
2. **4.0, contract.**
   - The setting becomes on for every site.
   - A migration drops the global keys.
   - **Rollback to the last 3.x:** that code honours the setting, so it works on a schema without the global keys. Rolling
     back to an older 3.x is not supported once duplicates exist. It would refuse to save one of two `kontakt` pages
     ("already exists") but would still serve both.
   - **Full schema rollback** means re-adding the global key. A script first renames the duplicates (`kontakt-en`) and
     writes redirects for them. Document it, test it, and do not automate it.

**As built in 3.9 (migration 0083, `Core\Slug`).** A site that has to move a bilingual WordPress site with the same slugs
(ictnwt.cz) cannot wait for 4.0, and with the global key in place no second `kontakt` can be stored. So step 1 ships the
per-language keys on every site and keeps the global keys, but switching `slugs_per_language` on (Settings → General,
"The same address in every language", only with Language versions on) drops the global keys of that one site
(`Slug::switchPerLanguage`); switching it off puts them back and is refused while two versions share a slug. The setting
is off by default on existing *and* new installs, so the schema of a fresh install equals an upgraded one and nothing
changes until the owner asks for it. A Kaleta export whose rows share slugs switches it on in the importing site before
the first row. The 4.0 contract migration can drop the global keys unconditionally: a missing index (error 1091) is
already treated as applied by `Core\Migration`.
- **Rollback of such a site to 3.8** (tested with the 3.8.0 code on a 3.9 database): both pages and both categories are
  served in their versions; the English news item of a shared slug is unreachable (3.8 finds the Czech one and redirects
  to it); saving either page of a shared slug is refused ("A page with this URL already exists"), everything else works.
  Content is never lost. Redirects stored with a prefix (`en/old`) do not fire in 3.8.

**Risks:**
- Code that reads `WHERE seo_link = ?` without a language and takes the first row. That is about 30 places; a unit test
  must grep for them, like the existing early-route guard.
- Redirect ambiguity during the transition.

**Effort:** M.

## 4. Czech table and column names to English

### Evidence

- **Tables:**
  - About 46 of the 92 tables have Czech names, for example `ka_novinky`, `ka_stranky`, `ka_nastaveni` and
    `ka_presmerovani`.
  - Everything since 1.5 is English: `ka_newsletters`, `ka_bookings`, `ka_facts`, `ka_agent_*`.
  - Code reaches the Czech ones through 892 placeholder uses such as `{novinky}`, and the core three appear in 66 files.
- **Columns:**
  - The 725 columns follow the same split.
  - Short legacy identifiers stay: `idc` (news), `idt`/`tema` (category), `ido` (media), `idu` (user) (`CLAUDE.md`,
    "Tabulky").
  - INV-15 counts the keys in PHP arrays: `'nazev'` 521×, `'typ'` 519×, `'jazyk'` 321×.
- **The MCP boundary is already English:**
  - `Mcp\Translator` (857 lines, 90 KB) maps tool names, parameters and result keys.
  - `Mcp\Vocabulary` (30 KB) maps the builder JSON.
  - Both are hand-kept. The public contract in `tools/contracts/mcp-tools.json` records only the English surface.
- **The export format mirrors the physical names:**
  - `obsah.json` keys are table names, and rows are `SELECT *` (`SiteExport.php:115-160`).
  - The header itself is Czech: `"verze_formatu"`, `"vytvoreno"`, `"nastaveni"`.
  - The format is versioned (`FORMAT_VERSION = 2`, `SiteExport.php:24`).
- **Add-ons get the whole `App`** (`Extension/Api.php:127`), and with it `db()`. Any add-on that queries a core table by
  placeholder depends on the Czech name.
- **The migration chain:** migrations 0001–0081 use the Czech names. On an old site they always run before any rename, so
  they never need to change.

### How each consumer copes with a rename

- **MCP and Translator.**
  - Tool and parameter names are English already and keep their Czech aliases, so nothing changes for connections.
  - Result keys are translated today. After a rename they become identity mappings, so the `MESSAGES` and `TOOLS` tables
    shrink rather than change.
  - The contract check stays green, because it records the English surface only.
  - The builder JSON (`stavba`: `deti`, `typ`, `obsah`) is data inside a column, not a column name. It stays Czech and
    `Vocabulary` stays. That is a separate decision.
- **The parity map in `tools/unit-tests.php`** lists admin actions and MCP tools, not columns, so it is unaffected.
- **Export and import.**
  - Export becomes format 3 with English keys.
  - `SiteImport` keeps a reader for format 2 that maps the old names through the same rename map. An export from a 3.x
    site must import into 4.0 forever, and a format-3 export into a 3.x site is refused with a clear message, as today
    for newer formats.
- **Migration chain.** The rename is migration N.
  - `tools/test-migrations.sh` compares the migrated schema with the new English `schema.sql`, as it does today.
  - Every later migration uses English names.
  - Hand-written SQL in data migrations (`.php`) goes through placeholders and so through the rename map.
- **Add-ons.** For one major release, `Db::sql()` resolves both the old and the new placeholders (`{novinky}` and
  `{news}`) to the physical table. The column names they use are their own problem, so this needs an announcement in
  `docs/EXTENSIONS.md` one release ahead.

### Options

| | Option | Effort | Risk |
|---|---|---|---|
| A | Never rename. English only at the boundaries (MCP, export v3 keys, docs) | S | none |
| B | Big-bang physical rename of tables and columns in 4.0 | XL (all SQL, all array keys, all views) | high: one missed `'nazev'` is a blank field on a live site |
| C | Rename **tables** physically (atomic `RENAME TABLE`) and keep the columns; placeholder aliases for one major | M | low |
| D | Per-entity rename with compatibility **views** under the old names | L per entity | `MATCH … AGAINST` and `FULLTEXT` do not work through views, so search would break on a rollback |

### Recommendation

- **3.x:**
  - Create one machine-readable rename map (`system/sql/names.php`: table, then columns, Czech to English).
  - Generate from it the result-key part of `Translator`, the format-3 export keys, and the developer docs.
  - Add the English placeholder aliases to `Db::sql()` (`{news}` and `{novinky}`).
  - Rule for new code: English placeholders and English columns in new tables, as since 1.5.
- **4.0:** option C.
  - Table renames are metadata-only and atomic, so there is no downtime.
  - Old placeholders keep resolving. Rolling back to the last 3.x works because its `Db::sql()` already knows both names.
    That is why the alias ships in 3.x first.
- **Columns:** do not rename them physically in 4.0. The prerequisite is a typed data-access layer per entity (repositories
  that own their column list, the way `Front\NewsRepository::LIST_COLUMNS` does for news). With that layer, renaming the
  columns of one table is a one-file change plus `ALTER TABLE … RENAME COLUMN`. `RENAME COLUMN` is in-place on MySQL 8 and
  MariaDB 10.5.2+.

### Rename map: the core tables (identifiers and the most-read columns)

| Today | English | Columns (today → English) |

## 5. Right-to-left languages (Arabic for fysiomed.eu)

### Evidence

- **The need.** Half of fysiomed.eu is Arabic: `/ar/`, `<html dir="rtl" lang="ar">`, about 400 URLs. The migration
  inventory calls this the "top gap 1" and a **blocker**.
- **Language list.** `Language.php:22` says Arabic and Hebrew "are not available yet – templates and the builder do not
  account for them". `ar` and `he` are two-letter codes, so RTL does **not** depend on §2.
- **Templates.**
  - The site template writes `<html lang="…">` with no `dir` (`views/front/base.php:32`).
  - The newsletter hard-codes `dir="ltr"` (`views/email/newsletter.php:28`).
- **CSS.**
  - Physical properties (`margin-left`, `padding-right`, `left:`, `text-align: left`) appear in `image/sablona.css` 6×,
    `image/web.css` 15×, `image/admin.css` 39× and `image/stavitel.css` 19×.
  - Logical properties appear in `sablona.css` 7× and `web.css` 6×.
- **The builder style is mostly logical already:** `padding-inline`, `margin-inline-start/end`, `border-block-*`,
  `text-align: start|end`. The exceptions are `zleva`/`zprava`, which write `left`/`right` (`Builder/Style.php:109-110`),
  and the gradient presets (`135deg`, radial `at 25% 15%`).
- **Scripts.** The lightbox and the carousel bind `ArrowLeft`/`ArrowRight` to previous/next (`image/web.js:59-60,183`).
  Those must swap in RTL.
- **Search and slugs are Latin-only:**
  - `Search::normalize` keeps only `a-z0-9` (`Search.php:17-19`), so Arabic, Hebrew, Greek, Cyrillic and CJK text is not
    searchable at all.
  - `slugify()` maps only Czech/Slovak/German diacritics and returns `n-a` for an Arabic title (`helpers.php:29-41`).

### Needs (none of them is a schema change)

1. **Languages and direction.** Add `ar`, `he` and `fa` to `Language::AVAILABLE` with a direction. Add a function
   `Language::dir()` that `base.php` writes as `<html dir>`. The newsletter template and the e-mails take the same value.
2. **Visitor CSS.** Convert the physical properties in `sablona.css` and `web.css` to logical ones (about 21 places). This
   changes nothing for LTR sites, because `inset-inline-start` is `left` in LTR. It is safe in 3.x.
3. **Builder.**
   - Render `zleva`/`zprava` as `inset-inline-start`/`end`. The stored values stay; only the CSS changes, and that CSS is
     identical in LTR.
   - Mirror the directional gradients in RTL with `:dir(rtl)`, or leave them as artistic choices. Decide.
   - The builder canvas iframe takes the `dir` of the page language.
4. **Admin.** It stays LTR (admin languages are cs, en and de). Content fields of an RTL version get `dir="auto"`, and
   names and e-mails in lists get `<bdi>`.
5. **Scripts.** Swap the arrow keys in RTL, and mirror the icons that point (→) with `:dir(rtl)`.
6. **Search.** Use Unicode-aware normalization (`\p{L}\p{N}` after removing diacritics). The tokens of existing Latin text
   do not change. The index refills through `Search::complete`.
7. **Slugs.** Keep ASCII slugs. For Arabic, the editor or Claude sets the slug (fysiomed already uses Latin `-ar` slugs).
   The `n-a` fallback becomes `page-<id>`. Unicode slugs would need percent-encoded routing and redirects (the routes use
   `[a-z0-9-]`); not now.
8. **Fonts.** The design system's system-font stacks render Arabic. Custom fonts must declare their Arabic subset. Audit
   warns when the RTL version uses a font without Arabic glyphs, if that can be detected; otherwise it is documented.
9. **Tests.**
   - A browser test renders an `ar` version: `dir=rtl`, the header layout mirrored, the carousel keys swapped.
   - The axe check stays green.

**Migration:** none for data. The CSS changes are invisible on LTR sites, and a before/after screenshot comparison of the
three starter sites proves that.

**Rollback:** code only.

**Effort:** M for Arabic on the visitor site, plus S for the importer, which maps the Polylang `ar` to the Arabic version.

## 6. Dates in the site's wall time vs UTC (INV-17)

### Evidence

- The schema has 142 `DATETIME` and 21 `DATE` columns, and no `TIMESTAMP`.
- PHP writes wall time with `date('Y-m-d H:i:s')` (260 places) in the site's zone (`App::applyTimezone`, `App.php:78-81`).
- SQL compares with `NOW()` (135 places). For that, each connection sets `SET time_zone = '<offset>'` from `date('P')`
  (`Db.php:55`). An offset, not a zone name, is used because named zones need time-zone tables that shared hosting lacks.
- Consequences:
  - **The DST overlap is ambiguous.** On 25 October 2026, 02:00–02:59 in Europe/Prague happens twice. Rows written in the
    second pass sort before rows from the first, and "within the last hour" checks can be off by an hour around the switch.
  - **Changing the `time_zone` setting moves every stored moment.** No conversion runs
    (`Admin/Modules/Settings.php:53` only validates the zone). A site that moves from Prague to London republishes its
    scheduled items an hour off, and its statistics days shift.
  - **Tests.** CI MySQL runs in UTC, which produced five "site clock" fix commits (INV-17). `tools/test.sh` now forces
    UTC sessions and `site_time` helpers.
  - **Exports carry wall times without a zone.** An import into a site with another zone shifts them.

**Not every date is a moment.** Two kinds of column must be told apart:
- **Instants:** created, updated, sent, logged, publish-at, expires. These should be UTC.
- **Civil times** that are meant on the local clock:
  - a booking at 10:00 (`ka_bookings`)
  - opening hours and exceptions (`ka_hours_exceptions`, `company_hours`)
  - the hours of an event in collection data
  - daily statistics buckets (`ka_stat_dny.den`)

  These must stay local, or a 10:00 appointment becomes 11:00 after a zone change.

### Options

| | Option | Notes |
|---|---|---|
| A | Keep wall time (status quo) and document it | Ambiguous hour, zone changes shift data |
| B | `TIMESTAMP` columns (MySQL converts by session zone) | Range ends in 2038 on MySQL; MariaDB extended it only in 11.5; the session offset trick makes conversions wrong across DST – **no** |
| **C** | **Instants as UTC in `DATETIME`, civil times stay local; one `Clock` helper for writes and comparisons (recommended)** | Session `time_zone = '+00:00'`; PHP converts on display |
| D | Instants as `BIGINT` epoch | Unreadable in SQL tools and exports; every `NOW()` and `INTERVAL` rewritten |

### Recommendation and migration (C)

1. **3.x, preparation (S):**
   - Changing `time_zone` in Settings warns, and offers to convert the stored instants by the old and new zone (a data
     job), or keeps them. This stops the silent shift now.
   - Add a `Clock` helper with `now()`, `toDb()` and `fromDb()` that every new write uses. In 3.x it still produces wall
     time, so it changes nothing yet; it only collects the call sites.
2. **4.0, expand and migrate (L):**
   - Classify every `DATETIME`/`DATE` column as instant or civil in the rename map (`names.php`).
   - A setting `db_clock` (`local` | `utc`) is stored per **table** as it is converted.
   - A background job converts instant columns table by table. It runs in batches by primary key, and each value is
     converted with PHP `DateTimeZone` at its own date, so DST is handled. Ambiguous values (the repeated hour) take the
     first occurrence, are counted, and are reported.
   - `Clock` reads the per-table flag, so a half-converted site stays correct.
   - The session becomes `+00:00`, and `NOW()` in queries on converted tables compares UTC with UTC. Queries on
     unconverted tables use `Clock::nowLocal()` passed as a parameter instead of `NOW()`. The 135 `NOW()` sites are
     rewritten to parameters in 3.x as part of the `Clock` work, which also makes the tests independent of the database
     zone.
3. **Rollback.** The conversion is reversible: the job runs in reverse by the stored flag, and the repeated hour is the only
   lossy part, which the report already names. The 4.0 code with `db_clock=local` behaves like 3.x, so "rollback" can
   also be just switching the flag back after the reverse job.
4. **Export format 3** writes instants in ISO 8601 with `Z` and civil times without a zone. Import converts format 2
   values from the exporting site's zone, which format 3 records in the header.

**Risks:**
- A missed `NOW()` on a converted table shows items an hour or two early or late. The guard is a unit test that forbids
  `NOW()` in queries on tables marked `utc` in `names.php`.
- Statistics days must stay local: `ka_stat_dny` is civil.

**Effort:** L. It is the largest item in this document, and it should not share a release with the table renames.

**What really needs 4.0:**
- dropping the global slug keys, because older 3.x code would refuse edits
- the physical table renames, because add-ons that use raw placeholders need the major-version signal
- export format 3

Everything else can ship in 3.x behind defaults that keep today's behaviour.

## 8. Open questions for the owner

1. **Collation:** is the recommendation acceptable: keep `utf8mb4_czech_ci` storage and sort per language with
   `COLLATE`? Or do you want language-neutral storage for new non-Czech installs, which means two schemas to test?
2. **Arabic:** is fysiomed.eu's Arabic half worth bringing RTL forward to 3.8–3.9, ahead of the per-language slugs? Arabic
   needs no BCP 47 work. Or should fysiomed move English-only first (inventory option "drop Arabic")?
3. **Slugs:** may Arabic (and later Greek or Cyrillic) versions use Latin slugs set by the editor or Claude, or do you want
   native-script URLs? Native scripts mean percent-encoded routing and a bigger redirect story.
4. **`zh`:** should the existing two-letter `zh` mean Simplified (`zh-Hans`)? Which regional variants do your sites need
   first (`pt-BR`, `en-GB`, `de-AT`)?
5. **Tags:** should tags get a language column in 4.0, or stay shared across languages as today?
6. **Renames:** is "tables in 4.0, columns after repositories (5.0)" acceptable, or do you want physical English column
   names in 4.0 regardless of the XL effort and risk?
7. **UTC:** is it acceptable that UTC storage lands in 4.1 rather than 4.0, so that it does not share a release with the
   renames? And may a `time_zone` change in 3.9 convert stored instants by default (with a choice to keep them)?
8. **Add-ons:** do any add-ons in the wild query core tables directly? If none do, the placeholder aliases can be removed
   in 4.1 instead of 5.0.
